# Shifat Smart-MCP Suite — Design

Date: 2026-04-27
Author: Shifat + Claude (brainstorming session)
Status: Design approved, awaiting implementation plan

## Goal

Build a personal MCP-server toolbelt for Shifat to operate personal infrastructure from any MCP-aware client (Claude Code, Codex, Cursor) without leaving the editor. Six MCPs in priority order:

1. `vercel-smart` — Vercel project, deploy, domain, env, log, analytics ops
2. `runpod-smart` — Runpod GPU pods: launch, stop, monitor, billing, templates, serverless endpoints (moved up to #2 on 2026-04-27 per Shifat directive after $500 OpenAI Parameter Golf credit grant)
3. `gsc-smart` — Google Search Console: sitemaps, indexing, queries, issues
4. `ga-smart` — Google Analytics 4: reports, funnels, attribution
5. `hetzner-smart` — Hetzner Cloud: VMs, snapshots, firewalls, metrics
6. `coolify-smart` — self-hosted Coolify: app status, redeploys, env edits, logs

| # | Decision | Rationale |

| 5 | Monorepo at `/home/oneknight/projects/tools/smart-mcps/` | Shared `packages/core` library; existing `clickup-smart-mcp` stays separate |
| 6 | Multi-MCP-client install (Claude Code + Codex + Cursor on Shifat's machine) | Single machine, no cloud sync, no npm publishing |
| 7 | Tools stay separate (clickup-smart pattern), no action-enum consolidation | Cleaner naming preferred over token savings |
| 8 | Approach 1 chosen over Approach 2 (codegen) and Approach 3 (smart-only) | See "Approaches considered" below |

## Approaches considered

### Approach 1 — Hand-coded breadth (CHOSEN)
Every tool hand-written: smart shortcuts + fuzzy resolvers + thin wrappers per endpoint. Target ~40–60 tools per MCP (matches `clickup-smart`'s 39).
- Pros: clean tool names, hand-curated schemas, deliberate UX, full coverage
- Cons: manual updates when upstream APIs add endpoints (~5 min per new endpoint)

### Approach 2 — Codegen wrappers + hand-coded smart shortcuts
Auto-generate thin wrappers from each service's OpenAPI/discovery spec. Hand-code only the killer 10–20 smart shortcuts.
- Pros: free coverage of new API endpoints, less repetitive code
- Cons: machine-derived tool names (`vercel_v9_post_v9_projects_id_or_name_domains`), bloated tool list (deprecated/internal endpoints), inconsistent feel between hand-coded and auto-coded tools, single codegen library = single point of failure across all 5 MCPs

### Approach 3 — Smart shortcuts only
Skip thin wrappers. Build only the killer 15–25 shortcuts per MCP. Anything else → fall back to curl + token in shell.
- Pros: cleanest tool list, fastest to build
- Cons: coverage gap; user explicitly rejected ("what if I need them at some point I will be pissed")

### Per-MCP package shape
Each MCP is an independent npm workspace. Own `package.json`, own `dist/server.js`, own README. Imports `smart-mcp-core` as workspace dep.

### Stdio transport, no HTTP
All five MCPs are local stdio servers, registered in client configs with `command: "node"` + absolute path to `dist/server.js`. No HTTP endpoints, no auth tokens crossing the network.

## Shared core (`packages/core`)

### `auth.ts`
```ts
loadCreds<T extends Record<string, string>>(opts: {
  serviceName: string;
  required: (keyof T)[];
  optional?: (keyof T)[];
  configPaths?: string[];
}): T
```
Priority order: env vars → config file at `~/.config/<serviceName>.json` → MCP-passed env. Throws `AuthError` with the exact missing key if required creds are absent.

### `server.ts`
```ts
import { createMcpServer } from "smart-mcp-core";
import { tools } from "./tools/index.js";
import { creds } from "./client.js";
createMcpServer({ name: "vercel-smart", version: "0.1.0", tools, context: { creds } });
```
Wraps `@modelcontextprotocol/sdk`'s `Server` + `StdioServerTransport`. Handles list/call protocol, normalizes errors via the taxonomy.

### `http.ts`
- Auto-retry with exponential backoff on 429/5xx (3 attempts default, configurable)
- Configurable timeout (30s default)
- Bearer auth header injection from creds context
- Returns parsed JSON or throws typed `SmartMcpError`
- `DEBUG=1` enables stderr logging of full request/response cycles

### `errors.ts` — error taxonomy
| Class | Trigger | Recovery hint |
|---|---|---|
| `AuthError` | 401/403, missing creds | Exact env var to check |
| `RateLimitError` | 429 after retries exhausted | `Retry-After` wait duration |
| `NotFoundError` | 404, fuzzy zero-match | Top fuzzy alternatives |
| `ValidationError` | zod validation, 400 with detail | Allowed values from schema |
| `ConfirmRequiredError` | Destructive op without `confirm: true` | Full diff as preview |
| `UpstreamError` | 5xx, unexpected response shape | Error code, request ID |
| `AmbiguousMatchError` | Fuzzy match below auto-pick threshold | Top 3 with scores |

Upstream API errors are formatted as: rewritten leading line + raw upstream as `detail` field. (Decision: option C from brainstorming.)

### `confirm.ts`
Helper for destructive ops. Tool input includes `confirm: z.boolean().default(false)`. If `confirm !== true`, throws `ConfirmRequiredError` with the proposed change as preview text.

```ts
guardDestructive({
  confirm: input.confirm,
  preview: `Will delete env var ${input.key} from ${input.project}`,
});
```

All write/destructive ops in smart shortcuts default to confirm-required. Read-only ops (`list_*`, `get_*`, `*_audit`, `daily_status`) never require confirm.

### `fuzzy.ts`
Levenshtein-based ranker. Used inside `smart_*` tools.
```ts
fuzzyRank(query: string, items: T[], extractor: (t: T) => string)
  : Array<{ score: number; item: T }>
```
- Auto-pick threshold: 0.9 (top match score must exceed this for auto-select)
- Below threshold → `AmbiguousMatchError` with top 3 alternatives

## Auth strategy per MCP

| MCP | Required env | Optional env | Special |
|---|---|---|---|
| vercel-smart | `VERCEL_TOKEN` | `VERCEL_TEAM_ID` | Plain bearer token |
| gsc-smart | OAuth refresh token in config file | none | One-time `gsc-smart-auth` CLI for OAuth flow |
| ga-smart | OAuth refresh token in config file | `GA_DEFAULT_PROPERTY_ID` | One-time `ga-smart-auth` CLI for OAuth flow |
| hetzner-smart | `HETZNER_API_TOKEN` | `HETZNER_PROJECT_ID` | Plain bearer token |
| coolify-smart | `COOLIFY_API_TOKEN`, `COOLIFY_BASE_URL` | none | Plain bearer token |
| runpod-smart | `RUNPOD_API_KEY` | `RUNPOD_DEFAULT_GPU` | GraphQL API (Runpod uses GraphQL not REST) — http.ts will need a `graphqlQuery` helper added in `packages/core` when this MCP lands |

Google MCPs (gsc, ga) require OAuth, not API keys. Each ships a one-time `<mcp>-auth` CLI command that opens a browser, completes OAuth, and writes the refresh token to `~/.config/<mcp-name>.json`. Day-to-day usage afterward is identical to the bearer-token MCPs.

## Data flow — example: `flip_canonical`

Walk-through of the smart-shortcut template (resolve → diff → confirm → apply → verify → structured return):

1. **Server entry** receives `tools/call`, parses + zod-validates input
2. **Fuzzy project resolution** via `smartProject(partial_name)` → top match if score > 0.9, else `AmbiguousMatchError`
3. **Domain inventory** via `client.listProjectDomains(projectId)`
4. **Compute diff** between current state and requested target
5. **Confirm gate** via `guardDestructive({ confirm, preview: <diff> })`
6. **Apply changes** via 1+ HTTP calls. Best-effort rollback on partial failure.
7. **Verify** with curl-style fetch to confirm expected status codes (CDN propagation may take ~30s, retry up to 3 times)
8. **Return structured JSON** — `{ ok, before, after, changes[], verified_at }`

Thin wrappers skip steps 4, 5, 7 — just resolve → apply → return.

## Testing

### Three layers
1. **Unit tests** (mocked HTTP via `msw`) — primary. Per-tool, covers happy path + error classes + fuzzy edges + confirm gate. ~5s full suite per MCP. Required to pass before commit.
2. **Schema lint** (`scripts/schema-check.ts`) — manual/cron. Hits real APIs with known fixtures, reports drift between expected response shapes and actual.
3. **Live smoke test** (`npm run smoke`) — manual, before deploying. Read-only tools only. Real creds. ~10s.

### Tooling
- Test runner: `vitest`
- HTTP mocking: `msw`
- No coverage gates

### What we don't test
- The MCP protocol layer (`@modelcontextprotocol/sdk` is trusted)
- Cross-MCP integration (each MCP is independent)
- Multi-client install (manual verify on first run)
- Performance / load (single user)

### Pre-commit hook
`npm run lint && npm run typecheck && npm test` — wired up via simple shell hook. **Off by default.** Personal toolbelt; friction kills momentum.

## Mitigations for token cost across MCP clients

Modern Claude Code uses deferred tool loading — schemas only enter context when a tool is invoked. So registering 5 MCPs adds ~5–10K tokens for tool name list, ~200–400 tokens per unique tool actually called. Manageable.

Other MCP clients (Codex, Cursor, older Claude Desktop) may eager-load all schemas, costing ~125K tokens for 500 tools. To stay viable in eager clients:
- Tool descriptions kept terse (~15 tokens, not paragraphs)
- Target ~40–60 tools per MCP (matches clickup-smart's 39)
- Per-session enable/disable via `/mcp` (Claude Code) or config comment-out (Codex)
