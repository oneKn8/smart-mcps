# email-smart-full (Phase 3.5) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to execute this plan task-by-task. Each task gets fresh implementer + spec reviewer + code quality reviewer subagents.

**Goal:** Close the gap between Phase 3 MVP and a complete email MCP. Add the features the live smoke pass surfaced as missing: attachments, threading, bulk send, bulk-unsubscribe, drafts CRUD, optional SMTP transport for accounts where OAuth Desktop is blocked.

**Why now:** Phase 3 shipped 18 tools end-to-end-verified against real Gmail (3 sends landed, label apply confirmed, inbox read/search/dry-run all green). User flagged that "MVP" framing under-delivered on the original ask: comprehensive Gmail MCP, not just the safe slice. This phase finishes the job.

**Architecture:** No new packages. Extends `packages/email-smart/`. Adds new TS modules (`smtp.ts`, `drafts.ts`, `attachments.ts`), extends `mime.ts` (multipart/mixed), extends `EmailClient` with draft + send-loop methods, adds 8-9 new tools. Reuses existing OAuth jar, identity loader, audit log, slim mappers.

**Tech Stack:** Same as Phase 3 — TypeScript 5.7 ESM, Node 22+, vitest 2.1, msw 2.6, zod 3.24. New runtime dep: `nodemailer` ^6.9 (only if SMTP transport ships in this phase). No core changes required.

**Tools shipping in this phase (8-9):**

1. `send_with_attachment` — multipart/mixed MIME with file attachments (path or base64-data inputs)
2. `compose_thread` — reply-to-message helper that sets `In-Reply-To` / `References` headers automatically
3. `bulk_send` — multi-recipient with per-recipient rate limit + per-recipient `vars` substitution
4. `bulk_unsubscribe` — parse `List-Unsubscribe` / `List-Unsubscribe-Post` headers, hit URL or send mailto, then archive
5. `create_draft` — create a draft (no send)
6. `list_drafts` — list drafts (slim shape)
7. `send_draft` — send an existing draft by ID (destructive)
8. `update_draft` — modify draft body / recipients
9. `delete_draft` — destructive, removes draft permanently (different from trash)

**Optional 10th tool (SMTP path, conditional):**
10. SMTP transport adapter inside existing `send_email` — only needed if user's UTD or other Workspace EDU account blocks third-party OAuth Desktop. Detection: `identity.transport === "smtp"`. No new TOOL, just transport branching.

After this phase: **email-smart total = ~26-27 tools, ~370+ tests.**

**Notes baked in:**
- All draft tools require `account: string` per the multi-account rule. No silent default.
- `bulk_send` is destructive — `confirm` + per-recipient `dry_run`. Output includes per-recipient gmail_id or error so the LLM caller can re-run failures.
- `bulk_unsubscribe` is destructive (it sends mailtos and/or hits URLs that may unsubscribe you elsewhere). Hard rule: NEVER hit unsubscribe URLs without `confirm: true`. `dry_run: true` (default) just lists what WOULD be unsubscribed.
- `compose_thread` reuses `send_email` internals — it's a thin wrapper that fetches the original message, extracts `Message-ID` header, builds `In-Reply-To`/`References` chain, then calls send_email with those headers. No new MIME code needed.
- `send_with_attachment` extends `mime.ts` to produce multipart/mixed wrapping the existing multipart/alternative body part.
- Drafts use the Gmail Drafts API: `POST /users/me/drafts` (create), `GET /users/me/drafts` (list), `POST /users/me/drafts/{id}/send` (send), `PUT /users/me/drafts/{id}` (update), `DELETE /users/me/drafts/{id}` (delete).
- SMTP transport (if shipped this phase): nodemailer with App Password. Only `send_email` and `send_with_template` and `send_with_attachment` route through SMTP; all read/inbox-modify tools remain Gmail-API-only and reject SMTP-transport accounts (already implemented in Phase 3).

**Gmail API endpoints introduced this phase:**
- `POST /users/me/drafts` (create) — body `{ message: { raw: <base64url MIME> } }` → `{ id, message: { id, threadId } }`
- `GET /users/me/drafts?maxResults=N` (list) → `{ drafts: Array<{ id, message: { id, threadId } }> }`
- `GET /users/me/drafts/{id}?format=full` (read) — for update RMW cycle
- `PUT /users/me/drafts/{id}` (update) — same body as create
- `POST /users/me/drafts/{id}/send` (send) → `{ id, threadId, labelIds }`
- `DELETE /users/me/drafts/{id}` (delete) — 204 No Content

**Conventions for the implementer subagent:** Same as Phase 3 (strict TDD, `account: z.string().min(1)` required everywhere, `confirm` gate before any side effect, audit-log soft-fail wrap on send paths, NodeNext `.js` extensions, no emojis, no AI/Claude/Anthropic/former-employer mentions, conventional commits with `feat(email-smart): ...` scope).

## Task list

### Task 1: `send_with_attachment` — multipart/mixed MIME (TDD destructive)

Extend `src/mime.ts` with a `buildRawMessageWithAttachments` function that wraps the existing multipart/alternative body in an outer multipart/mixed with one or more file attachment parts. Add tool `send_with_attachment` in `src/tools/send-attachment.ts`.

**Attachment input shape** (one of two):
```ts
type AttachmentInput =
  | { filename: string; path: string; content_type?: string }
  | { filename: string; data: string; content_type?: string };  // base64-encoded data
```

**Tool input:** same as `send_email` plus:
```ts
attachments: z.array(attachmentSchema).min(1).max(10),
```

**Behavior:**
1. Load identity, reject SMTP transport (matches `send_email` pattern — until Task 10 adds SMTP).
2. For each attachment: if `path`, read file (NodeNext `fs.readFileSync(path)`); if `data`, base64-decode. Validate combined size ≤ 25MB (Gmail's hard cap is ~25MB for multipart/mixed messages).
3. Build raw MIME via new `buildRawMessageWithAttachments` (multipart/mixed wrapping multipart/alternative).
4. Confirm gate, send via `client.sendMessage`, append audit (with `attachment_count` field added to AuditEntry — backwards-compatible by making it optional).
5. Return same shape as `send_email` plus `attachment_count`.

**Tests:** ≥10 spanning attachment-by-path, attachment-by-data, multiple attachments, content-type inference (`.pdf` → `application/pdf`, `.png` → `image/png`, fallback `application/octet-stream`), size cap rejection, MIME structure validity (assert outer is multipart/mixed, body part is multipart/alternative, attachment parts are after body).

Commit: `feat(email-smart): send_with_attachment via multipart/mixed`

### Task 2: `compose_thread` — threading helper (TDD destructive)

A thin wrapper over `send_email` that fetches the original message's `Message-ID`, builds `In-Reply-To` and `References` headers, and forwards to `send_email`.

**Tool input:**
```ts
z.object({
  account: z.string().min(1),
  in_reply_to_id: z.string().min(1),       // Gmail message ID to reply to
  subject_prefix: z.enum(["Re:", "Fwd:", ""]).optional().default("Re:"),  // auto-prepend if absent
  to: z.string().optional(),                // overrides original sender if set
  cc: z.string().optional(),
  bcc: z.string().optional(),
  html: z.string().min(1),
  text: z.string().min(1),
  reply_to: z.string().optional(),
  headers: z.record(z.string(), z.string()).optional(),
  confirm: z.boolean().optional().default(false),
})
```

**Behavior:**
1. Load identity, reject SMTP if applicable.
2. `client.getMessage(account, in_reply_to_id, "metadata")` to fetch original headers.
3. Extract original `Message-ID` (from headers, case-insensitive). If missing, throw `ValidationError("original message <id> has no Message-ID header; cannot thread")`.
4. Extract original `From` (becomes the default `to` if not provided).
5. Extract original `Subject`. Prepend `subject_prefix` unless subject already starts with it.
6. Extract original `References` header (chain of prior message IDs). Build new `References = original_references + " " + original_message_id`.
7. Set custom headers: `In-Reply-To: <original_message_id>`, `References: <built chain>`. Merge with user-provided `headers`.
8. Forward to `send_email`.

**Tests:** ≥6 covering: original message has Message-ID → headers built correctly, original missing Message-ID → ValidationError, References chain extends correctly, subject_prefix not duplicated, `to` defaults to original `From` when absent, threaded message lands in same Gmail thread (verify thread_id on response).

Commit: `feat(email-smart): compose_thread reply helper with In-Reply-To/References`

### Task 3: `bulk_send` — multi-recipient with rate limit (TDD destructive)

Sends the same message body (with optional per-recipient variable substitution) to multiple recipients sequentially with rate limiting.

**Tool input:**
```ts
z.object({
  account: z.string().min(1),
  recipients: z.array(z.object({
    to: z.string().min(1),
    vars: z.record(z.string(), z.string()).optional(),     // per-recipient template vars
  })).min(1).max(50),
  subject: z.string().min(1),
  html: z.string().min(1),                                  // may contain {{vars}}
  text: z.string().min(1),
  reply_to: z.string().optional(),
  rate_limit_ms: z.number().int().min(0).max(10_000).optional().default(500),  // delay between sends
  dry_run: z.boolean().optional().default(true),
  confirm: z.boolean().optional().default(false),
})
```

**Output:**
```ts
{
  attempted: number;
  sent: Array<{ to: string; gmail_id: string }>;
  failed: Array<{ to: string; reason: string }>;
  dry_run: boolean;
}
```

**Behavior:**
1. Load identity, reject SMTP, validate recipients (no duplicates).
2. `dry_run: true` → return preview with `attempted: recipients.length, sent: [], failed: [], dry_run: true`.
3. `dry_run: false` + `confirm: true`:
   - For each recipient sequentially:
     - Substitute per-recipient vars into html/text via `renderTemplate`.
     - Call `client.sendMessage`.
     - On success: push to `sent`, append audit.
     - On failure: push to `failed` with reason, continue.
     - `await sleep(rate_limit_ms)` between sends (skip after last).
   - Return `{ attempted, sent, failed, dry_run: false }`.
4. Hard cap recipients at 50 (Gmail per-day quota considerations; user can re-run for larger batches).

**Tests:** ≥10 covering dry_run path, sequential send, per-recipient vars, partial-failure resilience, rate limit honored, audit appended once per success, duplicate recipient rejection (zod-level).

Commit: `feat(email-smart): bulk_send multi-recipient with rate limit`

### Task 4: `bulk_unsubscribe` — List-Unsubscribe parser + action (TDD destructive)

The killer inbox-zero feature. Reads `List-Unsubscribe` and `List-Unsubscribe-Post` headers from a query of messages, hits the URL or sends mailto, then archives.

**Tool input:**
```ts
z.object({
  account: z.string().min(1),
  q: z.string().min(1),                                     // Gmail query
  max: z.number().int().min(1).max(100).optional().default(20),
  archive_after: z.boolean().optional().default(true),
  dry_run: z.boolean().optional().default(true),
  confirm: z.boolean().optional().default(false),
})
```

**Behavior:**
1. Load identity, reject SMTP.
2. List up to `max` matching message IDs.
3. For each message: `getMessage(format=full)`, parse `List-Unsubscribe` header. Format: `<https://example.com/unsub/abc>` or `<mailto:unsub@example.com?subject=unsubscribe>` or both comma-separated.
4. Build preview list: `[{ id, from_domain, unsub_url?, unsub_mailto?, subject }, ...]`.
5. Group by `from_domain` so the LLM/user can act per sender, not per message.
6. `dry_run: true` (default): return preview with `applied: false`.
7. `dry_run: false` + `confirm: true`:
   - For each unique `from_domain`:
     - Prefer mailto if `List-Unsubscribe-Post: List-Unsubscribe=One-Click` is set (RFC 8058 one-click); otherwise prefer URL POST; fall back to mailto.
     - Hit the URL via `fetch` (POST with `List-Unsubscribe=One-Click` body if one-click, GET otherwise) OR send mailto via `client.sendMessage`. Catch all errors per-attempt — don't let one failure abort the batch.
     - If `archive_after: true`, archive all messages from that domain via `client.batchModify(ids, removeLabelIds: ["INBOX"])`.
8. Output:
   ```ts
   {
     scanned: number;
     by_domain: Array<{
       from_domain: string;
       message_count: number;
       method: "url" | "mailto" | "none";
       attempted: boolean;
       success: boolean;
       reason?: string;
     }>;
     archived_count: number;
     dry_run: boolean;
   }
   ```

**Tests:** ≥12 covering parse `List-Unsubscribe: <https://...>`, parse `<mailto:...>`, parse both comma-separated, one-click POST detection, mailto fallback, archive after success, archive skipped on failure, dry_run path, partial-failure resilience, no `List-Unsubscribe` header → method: "none" + attempted: false.

Commit: `feat(email-smart): bulk_unsubscribe with one-click POST + mailto fallback`

### Task 7: SMTP transport adapter (TDD — conditional)

Add `src/smtp.ts`:
```ts
import nodemailer from "nodemailer";

export class SmtpClient {
  constructor(private readonly identity: Identity) {}
  async sendRaw(raw: string): Promise<{ id: string }>;
}
```

Identity yaml gains:
```yaml
transport: smtp
smtp_host: smtp.gmail.com
smtp_port: 587
smtp_user: <name>@<workspace.edu>
# password loaded from env: <ACCOUNT_NAME_UPPER>_SMTP_APP_PASSWORD
```

Send tool dispatch in `send_email` / `send_with_template` / `send_with_attachment` / `bulk_send` / `compose_thread`:
```ts
const result = identity.transport === "smtp"

  : await context.client.sendMessage(input.account, raw);
```

`compose_thread` and `bulk_unsubscribe` etc still need Gmail API for read paths, so SMTP-transport accounts can SEND but cannot use threading helpers (which need to fetch original) or bulk_unsubscribe (which needs to read inbox).

## What's NOT in this plan (deferred)

- **Filters CRUD** — `list_filters`, `create_filter`, `delete_filter`. Rare personal use. Skip.
- **Vacation responder** — `get_vacation`, `set_vacation`. Rare. Skip.
- **Permanent delete** (`gmail.delete` scope). Deliberate — never adding.
- **Real-time push (Pub/Sub watch)** — would require always-on infra. Skip.
- **Send scheduling** — Gmail's send-later API requires the `gmail.modify` scope (we have it) but adds tool surface complexity. Defer to a future polish.
- **Calendar invitations / iCalendar attachments** — out of scope for email MCP.
- **Per-recipient dry-run preview rendering** — could expand `bulk_send` dry_run output to show 3 sample rendered messages. Polish.
- **List-Unsubscribe RFC 8058 one-click POST verification round-trip** — the spec says POST should produce 200; we'll just accept 2xx without verification. Polish.
- **OAuth re-bootstrap automation** — currently requires user to manually run `bin/auth.py`. Could ship a TS bootstrap CLI eventually. Polish.

These are explicitly out of Phase 3.5 scope.
